# إصلاح حفظ الوارد في V10

هذا التعديل يخص `asker-nawaqes-test-10.html` فقط.

## التفعيل بالترتيب

1. افتح مشروع Supabase المرتبط بالتطبيق، ثم SQL Editor، ثم New query.
2. انسخ محتوى `migrations/202610170001_atomic_incoming.sql` بالكامل وشغّله مرة واحدة.
3. بعد نجاح SQL، انشر تعديل ملف V10 من هذا الفرع. عند غياب الدالة تتوقف الواجهة عن الحفظ وتحتفظ بالنص، ولا تستخدم الطلبين القديمين.

الدالة تعمل بصلاحيات المستخدم الحالي وتحترم سياسات RLS. لا تحتاج مفتاح service_role، ولا تحذف أو تعدّل أي سجل قديم. إذا فشل إنشاء الفهرس بسبب تكرارات قديمة، يتراجع تحديث SQL بالكامل؛ يجب فحص التكرارات قبل معالجة أي منها، دون حذف تلقائي.

يمنع الفهرس تكرار نفس `dedupe_key` حتى مع طلبين متزامنين. فحص الدفعات القديمة بدون مفتاح يظل موجودًا في الواجهة. عند انقطاع الاتصال قد تكون العملية قد اكتملت بالفعل؛ راجع السجل أولًا، وأعد المحاولة بنفس البيانات فقط حتى يبقى مفتاح منع التكرار ثابتًا.

## التحقق المنفذ

اختبار PostgreSQL محلي باستخدام PGlite وجداول تمثيلية، وليس قاعدة بيانات الصيدلية: نجاح حفظ الدفعة والأصناف، رفض المفتاح المكرر، فشل مرجع صنف بعد إدراج الدفعة والتراجع عن العملية كلها، رفض البيانات غير الصالحة، فشل RLS والتراجع، اشتراط الدخول، وإعادة تشغيل ملف التحديث. تم فحص صياغة JavaScript كذلك.

التشغيل: ثبّت `@electric-sql/pglite` خارج المشروع، ثم:

```sh
PGLITE_MODULE=/path/to/node_modules/@electric-sql/pglite node tests/atomic-incoming.cjs
```

لم يتم تطبيق SQL على Supabase الفعلي أو اختبار حفظ وارد حقيقي. مخطط الجداول وسياسات المشروع الفعلية غير موجودين في المستودع؛ تشغيل SQL على المشروع هو الخطوة اللازمة للتأكد من توافقهما. لا تعِد إدخال وارد قديم ولا تنشئ دفعة اختبار داخل بيانات العمل.
