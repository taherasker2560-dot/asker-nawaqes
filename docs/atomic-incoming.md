# إصلاح حفظ الوارد في V10

الحالة: الإصلاح جاهز للمراجعة واختُبر محليًا. لم يُطبّق على Supabase ولم تُنشر الصفحة المعدلة.

## المشكلة والتغيير

كانت V10 ترسل طلبًا لإنشاء `incoming_batches` ثم طلبًا مستقلًا لحفظ `incoming_items`.
فشل الطلب الثاني كان يترك دفعة بلا تفاصيل. التعديل يستبدلهما باستدعاء واحد
للدالة `save_incoming_batch_atomic`؛ أي فشل في إدخال الأصناف أو صلاحياتها يلغي
الدفعة وكل تفاصيلها ضمن معاملة واحدة.

الدالة تعمل بصلاحيات المستخدم (`SECURITY INVOKER`) وتحافظ على RLS والقيود
والقيم الافتراضية للأعمدة، ولا تضيف صلاحيات وصول للجداول. الاستدعاء متاح لدور
`authenticated` فقط ويتحقق من وجود جلسة دخول. تفشل migration إذا كان RLS
معطلًا على أحد الجداول. لا تتغير سياسات الجداول تلقائيًا.

تبقى الاقتراحات في حالة `possible` ولا تدخل في التغطية قبل تأكيد المستخدم.
يُحفظ منع التكرار السابق، ويُضاف فهرس فريد على `dedupe_key`. إذا كانت هناك
مفاتيح مكررة، تفشل migration دون حذف أو دمج أي سجلات.

الواجهة تحتفظ بالنص عند الخطأ أو غموض نتيجة الشبكة، وتحرر زر الحفظ في جميع
المسارات. لا تعود إلى طريقة الحفظ القديمة إذا لم تكن الدالة مثبتة.

## التحقق المنفذ

تشغيل `npm ci` ثم `npm test` يشغّل اختبارات PostgreSQL محلية باستخدام PGlite،
واختبارات لمنطق واجهة V10 باستخدام DOM وعميل Supabase محاكيين.

ثبت محليًا: حفظ الحالات الثلاث، التراجع الكامل عند فشل قيد في أحد الأصناف،
التراجع عند رفض RLS، منع التكرار، رفض هدف مطابقة غير متاح للمستخدم، رفض
المدخلات غير الصالحة والاستدعاء المجهول، وإعادة تطبيق migration دون تغيير
السجلات. اختبارات الواجهة تتحقق من إرسال RPC واحد، الاحتفاظ بالنص عند الخطأ،
والضغط المتكرر، وعدم استخدام إدخالات منفصلة عند غياب الدالة.

**الحدود:** مخطط الاختبار تمثيلي؛ لم نقرأ مخطط الإنتاج لأن طلب metadata أعاد
401 بدون جلسة دخول. هذه ليست اختبارات اتصال فعلي أو اختبار متصفحين متزامنين
أو تجربة على هاتف المستخدم، ولا تثبت سلامة سياسات الإنتاج القائمة.

## ترتيب التطبيق

1. تشغيل `supabase/preflight_atomic_incoming.sql` في SQL Editor. الملف للقراءة
   فقط ويعرض أنواع الأعمدة والقيم الافتراضية والسياسات والفهارس وأعدادًا إجمالية.
   مراجعة وجود الأعمدة المستخدمة، وصلاحيات SELECT/INSERT، وقيم owner الافتراضية
   إن وجدت، وتوافق سياسات إنشاء الدفعة وتفاصيلها. أي اختلاف يحتاج ضبط الإصلاح
   قبل التطبيق، دون طلب كلمة مرور أو service-role key.
2. تطبيق `supabase/migrations/20261016_atomic_incoming.sql` مرة واحدة، بعد
   مراجعة الفحص. يجب أن ينجح الملف بالكامل؛ عند أي خطأ لا ننشر تعديل الواجهة.
3. نشر تعديل `asker-nawaqes-test-10.html` بعد نجاح تحديث قاعدة البيانات.
   لا يتطلب التغيير نسخة V11، وملف `index.html` والنسخ السابقة لم يتغيروا.
4. التحقق على بيئة اختبار منفصلة بصلاحيات مماثلة قبل اعتبار الإصلاح معتمدًا.
   لا تُعاد دفعة قديمة ولا تُضاف بيانات تجريبية لقاعدة الصيدلية.

## نقاط لم تُعالج في هذا الإصلاح

- الدفعات القديمة الناقصة تحتاج مراجعة منفصلة؛ لا يحذفها الإصلاح.
- الصفحات الأقدم تظل تستخدم طريقة حفظها الحالية.
- قراءة النواقص للحفظ ما زالت بطلب واحد، وقد تتأثر بحد الصفوف في Supabase؛
  يلزم علاج pagination منفصل قبل الادعاء بتحميل جميع الأصناف.
- النسخ الاحتياطي يقرأ كل جدول بطلب واحد، والاسترجاع يكتب الجداول بالتتابع.
  لم يُصلح هنا اقتطاع النسخ عند حد الصفوف أو الاسترجاع الجزئي.
- لم تُضف مطابقة عربي/إنجليزي جديدة.
